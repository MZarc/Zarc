# PROJECT: Zarc the Private Gallery Vault — Rust Android Encryption Engine

## 1. Your role and mission

Act as a senior Rust systems engineer, Android security engineer, and application cryptography engineer.

Your task is to **implement a real, testable, security-conscious Android file-encryption engine written primarily in Rust**, packaged as an installable Android APK.

This is the foundation of a future private photo and video gallery inspired by Samsung One UI Gallery. The gallery interface will be built later.

For this phase, your priority is cryptographic correctness, key management, data-at-rest protection, reproducible testing, and honest security validation.

Do not merely produce an architecture proposal, tutorial, pseudocode, or checklist. Inspect the existing repository and environment, make a plan, implement the working code, run the available tests, build the APK, and report the actual results.

Never claim that the application is unbreakable, invulnerable, military-grade, or impossible to crack. Your task is to establish specific security properties through evidence.

## 4. Security scope and threat model

The primary security objective is:

> Protect private media stored by the application so that an attacker who obtains encrypted vault files, but not the necessary keys, cannot practically recover the original media using known cryptographic attacks.

The initial threat model should cover:

- Other ordinary, unprivileged Android applications.
- Someone copying the vault's stored files.
- Offline attacks against stolen vault data.
- Attempts to open ciphertext using common image and video decoders.
- Modified, truncated, reordered, duplicated, or substituted ciphertext.
- Incorrect keys, corrupt key envelopes, malformed files, and interrupted operations.
- Exposure through filenames, metadata, temporary files, logs, backups, and caches.
- Loss, corruption, or unavailability of the Android Keystore key.
- App crashes and process termination during encryption or decryption.

Explicitly document what is outside the protection guarantee:

- A compromised operating system or attacker with sufficient privileges on an already-compromised device.
- Malware or code executing inside the application while it has access to decrypted media or keys.
- Plaintext captured while a file is being viewed, exported, or otherwise used.
- Camera images, cloud copies, screenshots, or other copies the application does not control.
- Hardware vulnerabilities, future cryptographic breakthroughs, and implementation flaws that have not yet been discovered.

Do not use these exclusions to excuse preventable plaintext leakage or poorly managed keys.

## 5. Mandatory cryptographic design

### 5.1 Establish the primitive before implementation

The primary streaming-encryption candidate is libsodium's official `crypto_secretstream_xchacha20poly1305` construction.

Documentation:
https://doc.libsodium.org/secret-key_cryptography/secretstream

It provides authenticated streaming encryption suitable for large files.

Before selecting its Rust binding:

- Verify current crate documentation, source, release history, maintenance, license, known vulnerabilities, and Android cross-compilation support.
- Investigate `libsodium-rs` and the available maintained bindings to the official libsodium C API.
- Distinguish the security properties of upstream libsodium from the quality and maturity of an individual Rust binding.
- Verify the selected dependency can actually be built for the intended Android targets.

Select the most defensible implementation and record the rationale in `docs/CRYPTOGRAPHY_DECISION.md`.

If no suitable Rust binding can be validated, evaluate a narrowly scoped FFI integration with the official libsodium API or a well-supported Java/Kotlin streaming-encryption implementation such as Google Tink. Do not replace an unsuitable library with custom cryptographic code.

Do not silently select an unaudited crate merely because it is new, popular, fast, or easy to install.

Relevant alternative documentation:
https://developers.google.com/tink/streaming-aead

### 5.2 Content encryption

Use authenticated encryption with a fresh, independently generated 256-bit data-encryption key (DEK) for each stored object.

Requirements:

- Use a cryptographically secure random-number generator supplied by the chosen cryptographic library or platform.
- Process files incrementally using bounded-memory buffers. Never read an entire large video into RAM.
- Use a streaming construction designed for authenticated large-file encryption.
- Never invent your own cipher, key-generation method, nonce-management scheme, or chunk-authentication algorithm.
- Never reuse a key and nonce combination contrary to the chosen construction's requirements.
- Treat all cryptographic initialization, encryption, decryption, finalization, and authentication failures as explicit errors.
- Clear sensitive buffers on a best-effort basis using an appropriate zeroization library or the cryptographic library's secure-memory facilities.
- Document the limitations of memory zeroization in a managed operating system and Rust application's runtime environment.

Do not add arbitrary encryption layers. Do not triple-encrypt files with unrelated algorithms to create an appearance of security.

### 5.3 Key hierarchy

Implement and document a clear key hierarchy.

**Vault master key (VMK)**

- Generate a random 256-bit vault master key using a cryptographically secure generator.
- Never store it directly in plaintext on persistent storage.
- Do not embed any key in source code, application resources, configuration, test fixtures intended for production, or the compiled APK.

**Device key-encryption key (KEK)**

- Generate a non-exportable AES-256-GCM key using Android Keystore where supported.
- Use it to wrap and unwrap the VMK using Android's platform cryptographic APIs.
- Store only the authenticated wrapped VMK and its required parameters in private app storage.
- Check and report the actual available key security level. Prefer hardware-backed protection when supported; distinguish StrongBox from other hardware-backed implementations and software-backed Keystore.
- Never label a key hardware-backed without evidence from the Android platform.
- Handle unsupported algorithms, unavailable StrongBox, missing key aliases, and Keystore failures explicitly. Never silently fall back to writing a plaintext key.

**Per-object data key (DEK)**

- Generate an independent random 256-bit DEK for each object.
- Wrap the DEK under the VMK using an established authenticated-encryption API from the chosen cryptographic library.
- Generate fresh nonces as required by that API.
- Bind relevant object identifiers, format version, and key purpose as associated authenticated data.
- Verify authentication before accepting an unwrapped DEK.

Document the exact key hierarchy, all key transitions, and the consequences of losing either key layer.

The VMK will necessarily be usable by the Rust process during operations if Rust performs the file encryption. Keep its lifetime as short as practicable, avoid logging or unnecessary copies, and document residual process-memory exposure.

### 5.4 Recovery limitation

A recovery system is not required for this initial proof of concept.

However, document that device-only key protection can make the vault unrecoverable following app-data loss, key invalidation, or device replacement.

Do not invent a password-based recovery scheme. In particular, never derive a key directly from a password without an appropriate password-based key derivation function and reviewed parameters.

Design a documented extension point for a future recovery envelope, but do not pretend recovery exists if it has not been implemented and tested.

## 6. Opaque encrypted-file format

Create a versioned binary container for encrypted objects.

Requirements:

- Store objects under randomly generated opaque identifiers with no `.jpg`, `.jpeg`, `.png`, `.webp`, `.heic`, `.mp4`, or other media extension.
- Store all production vault objects in Android app-private internal storage.
- Use a documented, versioned container format with well-defined bounds, length handling, and error behavior.
- Include only the minimum information that must remain outside the encrypted content, such as the container version, random object identifier, stream initialization data, and authenticated wrapped-key envelope.
- Do not put the original filename, MIME type, media type, image dimensions, EXIF information, album name, GPS data, or capture timestamp in plaintext.
- Do not make encrypted objects recognizable as ordinary images or videos merely by inspecting their opening bytes.
- Do not claim that the existence of encrypted data is undetectable. Ciphertext sizes, storage usage, timing, and the application's identity can leak information.
- Authenticate the fields whose integrity matters. Do not trust unverified length fields or offsets.
- Reject malformed headers, unsupported versions, unreasonable sizes, integer overflow, invalid lengths, truncated fields, and trailing data where prohibited.

Use a random object identifier as the stored filename. Bind it into the relevant key-envelope authentication so that moving a valid envelope to another object does not make it valid in the wrong context.

The format marker may identify the object as belonging to the vault format, but it must not reveal the original media format.

Keep the encrypted object's format specification in `docs/FILE_FORMAT.md`.

## 7. Fail-closed encryption and decryption

### Encryption

1. Create a new temporary ciphertext object in app-private storage.
2. Generate a new DEK and initialize the streaming encryption operation.
3. Stream input data through the selected cryptographic library.
4. Write the complete authenticated final stream and wrapped-key envelope.
5. Flush and finalize output as appropriate for the platform.
6. Verify that the operation completed successfully.
7. Atomically commit the completed object under its final opaque identifier.

On failure, cancellation, or interruption, do not publish a partial file as a valid object. Clean up temporary ciphertext on a best-effort basis.

Never automatically delete the imported original.

### Decryption

1. Parse and validate the container.
2. Unwrap the file key only through the proper key hierarchy.
3. Decrypt to a restricted staging location, without exposing unverified output.
4. Validate the complete stream, including the required final authentication tag and end-of-file behavior.
5. Reject incomplete streams, trailing garbage where forbidden, and any authentication failure.
6. Commit the restored file only when the entire operation has been accepted as valid.

Do not expose partially authenticated plaintext to a media viewer, public directory, or other consumer.

For a failed decryption, remove the staging file on a best-effort basis and ensure the operation reports failure. Never return a successful result merely because earlier chunks decrypted successfully.

Clearly document that deletion from flash storage is not a guarantee of forensic erasure.

## 9. Mandatory validation suite

Create automated tests alongside the implementation. Tests must exercise the actual selected cryptographic library and file format.

### A. Round-trip tests

Cover at least:

- Empty input, with explicitly defined supported behavior.
- One-byte input.
- Inputs immediately below, at, and above the chosen chunk size.
- Multiple chunks.
- Multi-megabyte inputs.
- Arbitrary binary data.
- Representative JPEG, PNG, WebP, and video fixtures where available.

Encrypt and decrypt each supported fixture. Compare SHA-256 hashes of the original and restored bytes. Hash equality demonstrates data fidelity; it is not evidence that the cipher is strong.

### B. Ciphertext mutation tests

Deliberately test:

- Wrong DEK.
- Wrong VMK.
- Modified wrapped-key envelope.
- Modified container version and object identifier.
- Modified stream header.
- Modified ciphertext bytes.
- Modified authentication tags.
- Truncation at multiple offsets.
- Truncated final chunks and missing final authentication tags.
- Removed, reordered, duplicated, or substituted chunks where the format permits such mutations to be attempted.
- Extra bytes appended after the complete stream.
- Invalid lengths, malformed fields, oversized declared lengths, and integer overflow attempts.

Expected outcome: invalid encrypted objects are rejected, errors are explicit, and no invalid plaintext object is committed as successful output.

Use the streaming library's documented format and authentication semantics rather than assuming every possible mutation must fail at the same point.

### C. Key lifecycle tests

Test:

- Key generation produces valid key material.
- Different objects receive independent DEKs.
- The same input encrypted in independent operations does not yield identical ciphertext under fresh keys and initialization data.
- VMK wrapping and unwrapping survive application process restarts while the relevant Android Keystore key remains available.
- Corrupt wrapped VMK material is rejected.
- Missing aliases, invalidated keys, unsupported key operations, and wrong key material fail closed.
- The app never saves an unwrapped production key to persistent storage.
- Logs contain no keys, recovery secrets, plaintext file contents, or sensitive metadata.

Do not create misleading custom known-answer tests. Run the selected cryptographic library's official tests or published known-answer tests where available, and report which tests were actually executed.

### D. Crash and transactional tests

Test interrupted encryption, interrupted decryption, cancelled jobs, output-write failures, low-storage conditions where feasible, and process termination during a temporary operation.

The vault must not mistake incomplete output for a completed object. Test cleanup and recovery behavior rather than assuming the operating system always removes temporary files.

### E. Fuzzing and property-based tests

Add property-based tests for valid and invalid input streams and the binary container parser.

Where practical, add a fuzz target for container parsing and decryption boundaries using the available Rust fuzzing ecosystem. Run a bounded fuzz campaign if the environment supports it. Record limitations if fuzzing tools are unavailable.

Fuzz tests must never use real personal photographs or production vault keys.

### F. Android integration tests

Test the actual Android implementation, not only desktop simulations.

Verify, where the environment permits:

- Android Keystore key creation and wrapping/unwrapping.
- Persistence across an app process restart.
- Actual reported hardware/software security level.
- Correct behavior when StrongBox is unavailable.
- Correct failure behavior when a key is unavailable.
- Storage remains within the intended app-private location.
- No unexpected public-media or automatic-backup copies of the vault are created.
- The Android APK starts and can complete an on-device self-test.

A desktop unit test does not prove Android Keystore works correctly.

### G. Storage-leakage audit

Use synthetic, uniquely identifiable test fixtures.

After encryption, inspect the vault storage, databases, temporary files, logs, caches, backup configuration, and available application artifacts for unintended plaintext leakage.

Attempt to locate original image magic bytes, distinctive plaintext fixture markers, original filenames, metadata, and any unwrapped key material in files where they should not occur.

Distinguish a verified absence from a test that could not be completed. Do not claim that a finite search proves all plaintext is absent from every device location.

Where available, repeat the inspection on an emulator or dedicated test device with elevated privileges so the audit is not limited to an ordinary application's permissions.

Use the OWASP Mobile Application Security Verification Standard and Mobile Application Security Testing Guide as references for the security checklist:

- https://mas.owasp.org/MASVS/
- https://github.com/OWASP/masvs

MobSF may be used for additional static or dynamic analysis if available:
https://github.com/MobSF/Mobile-Security-Framework-MobSF

An automated scan is supporting evidence, not a security certification.

## 10. Engineering quality and dependency hygiene

Organize the project into clearly separated responsibilities, for example:

- Rust vault/encryption core.
- Versioned encrypted-file format and parser.
- Key management interfaces.
- Android platform adapter.
- Automated unit, integration, and adversarial tests.
- Minimal Security Lab test interface.
- Security and architecture documentation.

Keep the cryptographic module small and testable.

Use explicit error types. Never convert an authentication failure into an empty result or a success-shaped response.

Check all untrusted length fields and handle integer overflow safely.

Avoid `unsafe` in Rust unless demonstrably necessary. If FFI requires `unsafe`, confine it to a small module, document the invariants, and test its boundaries.

Pin resolved dependencies through the lockfile. Review licenses and known advisories using available tooling. Do not disable compiler warnings, lint rules, or failing tests merely to obtain a successful build.

Do not introduce an additional encryption algorithm without documenting the specific threat it addresses and why the additional complexity is justified.

## 13. Acceptance criteria

This phase is complete only when the following conditions have been addressed:

1. A functioning Rust encryption core exists.
2. The Android-specific key-protection integration is implemented, or a precisely documented blocker prevents it.
3. The Android APK builds when the environment supports the required toolchain.
4. Files can be encrypted and restored with byte-for-byte fidelity.
5. Invalid ciphertext, wrong keys, malformed containers, and incomplete streams are correctly rejected.
6. Incomplete operations cannot publish corrupted or unauthenticated results as completed files.
7. Persistent vault objects have opaque filenames and are not ordinary image/video files.
8. Original filenames and sensitive media metadata are not intentionally stored in plaintext vault metadata.
9. Key handling, backup behavior, and recovery limitations are documented and tested where feasible.
10. The validation report distinguishes PASS, FAIL, NOT RUN, and INCONCLUSIVE results.
11. No critical failures are hidden, waived without explanation, or described as successes.
12. The implementation does not claim to be unbreakable.

Do not stop when compilation succeeds. Compilation is only one part of the work.
