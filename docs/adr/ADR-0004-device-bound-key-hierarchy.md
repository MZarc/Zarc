# ADR-0004: A device-bound key hierarchy with no recovery path (yet)

* Status: Accepted
* Date: 2026-10-21

## Context

The vault master key has to be protected on a device that the user may lose,
that may be wiped and that may be replaced. The brief requires a documented
key hierarchy, a documented recovery limitation and a documented extension
point for a future recovery envelope.

## Decision

Zarc uses a **two layer, device-bound key hierarchy**:

```
Android Keystore key (non-exportable, AES-256-GCM, hardware backed when the
platform provides it)
   │  wraps / unwraps (AES-256-GCM, platform generated IV)
   ▼
Vault Master Key (VMK, 256-bit, random, generated by the platform adapter)
   │  wraps / unwraps (XChaCha20-Poly1305-IETF, fresh 192-bit nonce)
   ▼
Data Encryption Key (DEK, 256-bit, fresh for every object)
   │  encrypts
   ▼
Object content (XChaCha20-Poly1305 secretstream)
```

**There is no recovery envelope in this phase.** The wrapped VMK is stored in
`noBackupFilesDir` and can only be unwrapped while the Keystore key exists.

The extension point is the *envelope* layer: `VaultRepository.vaultMasterKey()`
is the single place where the VMK enters the system. A future recovery
mechanism (for example a passphrase-derived wrapping key, or a server side
recovery share) would be inserted there, as an additional way to obtain the
same VMK, without touching the container format, the DEK layer or the tests.

## Rationale

* **No plaintext key on disk.** The VMK exists in memory only, for the
  duration of a single operation, and is zeroized afterwards.
* **No invented recovery scheme.** A password based recovery would need a
  reviewed password based KDF with reviewed parameters. Shipping a home grown
  one would be worse than shipping none.
* **Fail closed.** If the Keystore key is missing, invalidated or the wrapped
  VMK does not authenticate, every operation fails. Zarc never falls back to
  an unprotected key.
* **The loss is explicit.** The instrumented test
  `losingTheKeystoreKeyDestroysTheVault` demonstrates that losing the
  Keystore key makes the old objects permanently unreadable. This is the
  documented cost of a device-bound hierarchy.

## Consequences

* App data loss, a factory reset, a wiped Keystore or a device replacement
  makes the vault unrecoverable. This is stated in the user interface and in
  `docs/KEY_MANAGEMENT.md`.
* Because the VMK is not backed up, the vault cannot be restored onto another
  device.
* A future recovery feature is a change in exactly one place
  (`VaultRepository.vaultMasterKey()`) plus a new test suite for the recovery
  envelope.
* Adding recovery later will change the security properties of the vault
  (the VMK would no longer be device-bound), so it deserves its own threat
  model and its own ADR.
